## 1. Blank invoice items on re-open (`b365f94`)

**Symptom:** INV-25-26-0001 opened and showed an empty Items section despite correct subtotal and total values.

**Root cause:** `InvoiceRepositoryImpl.update()` executed `DELETE FROM invoice_items WHERE invoice_id = ?` unconditionally before re-inserting items. If called with an empty list (e.g. from a hot-reload edge case), all rows were silently deleted. The totals on the `invoices` row survived, so amounts looked correct but items were gone.

**Fixes:**
- `invoice_repository_impl.dart` — skip delete+insert cycle when `items.isEmpty`; add `debugPrint` warning
- `quote_builder_screen.dart` — added `_saveInvoice()` early-return guard when items list is empty
- `invoice_detail_screen.dart` — show a warning banner in `_LineItemsCard` when items are blank but totals are non-zero

## 2. Quote detail showing stale status (`e2e6489`)

**Symptom:** QT-25-26-0006 showed "Accepted" badge in the list tile but "Draft" in the detail screen header.

**Root cause:** `quoteByIdProvider` (a `FutureProvider.family`) did a direct `getById()` DB fetch. The list screen read from the in-memory `quotesProvider`. These two sources could diverge — list updated via `load()` after conversion, while the detail screen re-fetched from the DB which might return a cached or stale row.

**Fix:** Both `quoteByIdProvider` and `invoiceByIdProvider` now read from the **same in-memory list** (`quotesProvider` / `invoicesProvider`) as the list screens, falling back to a DB fetch only while the list provider is still in its initial loading state.

## 3. Unhandled exception: `ref` used after widget disposed (`invoices_screen.dart`)

**Symptom:**
```
[ERROR] Unhandled Exception: Bad state: Cannot use "ref" after the widget was disposed.
_InvoiceTile.build.<anonymous closure>.<anonymous closure>
```

**Root cause:** `_InvoiceTile` and `_QuoteTile` are `ConsumerWidget`s. Both had `.then((_) => ref.invalidate(...))` on their `Navigator.push` call. If the widget was recycled or disposed during navigation, the `.then()` callback fired on a dead `ref`.

**Fix:** Wrapped both callbacks with `if (context.mounted)` before calling `ref.invalidate(...)`. Since `ConsumerWidget` ties `ref` to the same element as `BuildContext`, a mounted context guarantees a live ref.

## 4. "Convert to Invoice" button visible after conversion (`quote_detail_screen.dart`)

**Symptom:** After converting QT-25-26-0006 to an invoice, the detail screen still showed the "Convert to Invoice" bottom bar button and overflow menu item.

**Root cause:** `_canConvert` only checked `quote.status` but never checked whether a linked invoice already existed.

**Fix:** `_canConvert` now also calls `ref.watch(invoiceByQuoteIdProvider(quote.id!))` and returns `false` if a linked invoice is already present, reactively hiding both the bottom button and the overflow menu item as soon as conversion completes.

## 5. Quote-to-invoice conversion — 5 data integrity bugs (`4e2d668`)

All five bugs were in `QuoteRepositoryImpl.convertToInvoice()` and the surrounding provider/screen layer.

### 5a. `invoicesProvider` never reloaded after conversion

**Symptom:** After converting a quote, the Invoices list tab remained stale (new invoice absent). `_LinkedInvoiceCard` continued returning null because `invoiceByQuoteIdProvider` reads from `invoicesProvider` synchronously.

**Fix:** Injected a `reloadInvoices` callback into `QuotesNotifier`. `quotesProvider` factory wires it to `() => ref.read(invoicesProvider.notifier).load()`. Both lists are now refreshed after every conversion.

### 5b. Null-assert crash on conversion failure

**Symptom:** If `convertToInvoice()` returned `null`, `invoice!.id!` threw a `Null check operator used on a null value` that bypassed the `catch` block and showed no error to the user.

**Fix:** Added explicit null check for `invoice == null || invoice.id == null` before `Navigator.pushReplacement`, with a snackbar fallback on failure.

### 5c. `businessId` not copied to converted invoice

**Symptom:** Converted invoices had `businessId = null`, making them invisible in per-business filtered views.

**Fix:** `convertToInvoice()` now passes `businessId: quote.businessId` to the `Invoice` constructor.

### 5d. `freightAmt` / `insuranceAmt` / `packingAmt` not copied

**Symptom:** The converted invoice's total matched the quote (total was copied), but the individual surcharge fields defaulted to `0`. Re-editing the invoice would recalculate to a lower total.

**Fix:** All three surcharge amounts are now copied from `Quote` to `Invoice` in the constructor call.

### 5e. `hsnCode` / `unit` / `hsnOrSac` not copied to `invoice_items`

**Symptom:** HSN/SAC codes and GST Unit of Measure were silently dropped on conversion, breaking GSTR-1 data for invoices converted from quotes.

**Fix:** All three fields are now copied from `QuoteItem` to `InvoiceItem` inside the transaction loop.

### Bonus: Empty-items guard in `QuoteRepositoryImpl.update()`

Added the same `items.isEmpty` guard as `InvoiceRepositoryImpl.update()` to prevent silent deletion of all `quote_items` rows.

## 6. Quote business scoping and independent tab filters (`8f5c24f`)

### 6a. Quotes were cross-business (no `context_id` scoping)

**Symptom:** `QuoteRepositoryImpl.getAll()` returned every quote from every business context. New quotes inserted with `context_id = NULL`. Invoices created via `convertToInvoice()` also had `context_id = NULL` (bypassed `InvoiceRepositoryImpl.insert()`).

**Root cause:** `QuoteRepositoryImpl` had no `contextId` field, no `_ctx` getter, and no `context_id` stamping on insert — unlike `InvoiceRepositoryImpl` which has all three.

**Fixes:**
- `QuoteRepositoryImpl` constructor now accepts `contextId: int?`
- `_ctx` getter added (matches `InvoiceRepositoryImpl` pattern)
- `getAll()`, `getByCustomer()`, `getByPartyId()` all scoped by `_ctx`
- `insert()` stamps `context_id` on new quote rows
- `convertToInvoice()` stamps `context_id` on the created invoice row directly in the transaction
- `quoteRepositoryProvider` now watches `activeContextProvider` (same as `invoiceRepositoryProvider`)

### 6b. Date filter on one tab accidentally filtered the other tab

**Symptom:** Opening the date filter sheet on the Quotes tab and selecting "This Month" also filtered the Invoices tab (and vice versa), because both `filteredInvoicesProvider` and `filteredQuotesProvider` read from the same `invoiceDateRangeProvider` and `invoiceSearchQueryProvider`.

**Fix:**
- Added `quoteSearchQueryProvider` and `quoteDateRangeProvider` as independent `StateProvider`s
- `filteredQuotesProvider` now reads from these quote-specific providers
- `_FilterBottomSheet` accepts a `tabIndex` parameter; it reads/writes `quoteDateRangeProvider` when on the Quotes tab and `invoiceDateRangeProvider` when on the Invoices tab
